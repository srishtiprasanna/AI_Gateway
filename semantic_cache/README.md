# Semantic Cache

## What I learned

In this hands-on, I learned about **Semantic Caching** and how it can be used in an AI Gateway.

Normally, when a user asks a question, the request is sent to an AI model every time. If another user asks the same or a very similar question, the AI model generates the answer again.

This can increase:

- API usage
- Cost
- Response time

A semantic cache helps avoid this.

Instead of checking whether the question is exactly the same, it checks whether the **meaning of the new question is similar to a previous question**.

For example:

**Question 1:**  
What is the capital of France?

**Question 2:**  
Which city is the capital of France?

These questions are written differently, but they have almost the same meaning.

The semantic cache can recognize this and return the previous answer instead of calling the AI model again.

## What I built

I created a small **Semantic Cache Gateway** using:

- Python
- FastAPI
- Groq
- OpenAI-compatible API
- Sentence Transformers
- NumPy

The application has a `/chat` endpoint where I can send a question.

The gateway first checks the cache before calling the AI model.

---

## How it works

The basic flow is:

    User Question
          ↓
    Create Embedding
          ↓
    Compare with Cached Questions
          ↓
    Is the meaning similar?
        ↙       ↘
      Yes        No
       ↓          ↓
    Return      Call AI Model
    Cached          ↓
    Response    Store Response
                    ↓
              Return Response

The gateway does not immediately send every question to the AI model.

First, it converts the question into an embedding and compares it with the embeddings of previously cached questions.

If a similar question is found, the cached answer is returned.

If no similar question is found, the request is sent to the AI model and the new response is stored in the cache.

---

## What is an Embedding?

An embedding is a way of converting text into numbers.

For example:

    "What is the capital of France?"

is converted into a numerical vector.

Another question:

    "Which city is the capital of France?"

is also converted into a numerical vector.

Because the two questions have similar meanings, their vectors should also be similar.

I used the `all-MiniLM-L6-v2` model from Sentence Transformers to create these embeddings.

---

## What is Semantic Similarity?

Semantic similarity means checking whether two pieces of text have a similar meaning.

For example:

    What is the capital of France?

and

    Which city is the capital of France?

are not exactly the same sentence, but they have the same meaning.

The semantic cache uses this similarity instead of only checking whether the text is exactly the same.

---

## Similarity Score

After creating the embeddings, I calculate how similar two questions are.

I used **cosine similarity** for this.

The similarity value is generally between:

    0 → Very different
    1 → Very similar

I set a similarity threshold of:

    SIMILARITY_THRESHOLD = 0.60

If the similarity is greater than or equal to `0.60`, the gateway considers it a cache hit.

## Testing

I tested the semantic cache using two questions with the same meaning.

### First Request

I sent:

    What is the capital of France?

The response was:

    {
      "response": "Paris.",
      "cache_hit": false,
      "similarity": null,
      "model_used": "openai/gpt-oss-20b",
      "latency": 0.627
    }

Since this was the first question, there was no matching response in the cache.

So the gateway called the AI model and stored the response.

The important part was:

    cache_hit: false

This means the response was generated by the AI model.

### Second Request

I then sent a similar question:

    Which city is the capital of France?

The response was:

    {
      "response": "Paris.",
      "cache_hit": true,
      "similarity": 0.942,
      "model_used": "openai/gpt-oss-20b"
    }

The similarity score was:

    0.942

This was higher than my threshold of:

    0.60

So the gateway identified the question as similar to the previous question.

The important part was:

    cache_hit: true

This means the gateway returned the previously stored answer instead of making another AI model call.

## Without Semantic Caching

Without caching, the model is called every time:

    Question
       ↓
    AI Model
       ↓
    Answer

    Similar Question
       ↓
    AI Model
       ↓
    Answer

The model is called again even if it has already answered a similar question.

---

## With Semantic Caching

With semantic caching:

    First Question
          ↓
      AI Model
          ↓
        Answer
          ↓
      Store in Cache

    Similar Question
          ↓
      Check Cache
          ↓
    Similar Response Found
          ↓
    Return Cached Answer

The second request does not need to call the AI model.

---

## Why Semantic Caching is Useful

Semantic caching can be useful in AI applications because many users may ask similar questions.

For example:

    What is Python?

    Explain Python.

    Can you tell me what Python is?

    What does Python mean?

These questions are written differently but can have very similar meanings.

Instead of generating a new answer for every request, a semantic cache can reuse an existing answer when the similarity is high enough.

This can help with:

- Reducing repeated LLM calls
- Reducing API usage
- Reducing response latency
- Reducing cost
- Improving application performance

## Main API

### `GET /`

This checks whether the Semantic Cache Gateway is running.

Example response:

    {
      "message": "Semantic Cache Gateway is running"
    }

### `POST /chat`

This is the main endpoint.

I send a question like:

    {
      "message": "What is the capital of France?"
    }

The gateway then:

1. Creates an embedding for the question.
2. Checks the existing cache.
3. Calculates similarity with cached questions.
4. Returns the cached answer if the similarity is high enough.
5. Otherwise, calls the AI model.
6. Stores the new question and answer in the cache.
7. Returns the response.

## Important Note

The cache in this project is an **in-memory cache**.

This means the cached data is stored in the running Python application.

If I stop or restart the server, the cache is cleared.

For a production application, the cache could be stored in something like:

- Redis
- PostgreSQL with pgvector
- A vector database

A production implementation would also need things like:

- Cache expiration
- Better cache management
- Handling large amounts of cached data
- Protection of sensitive information
- More careful similarity thresholds
